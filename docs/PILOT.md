# Терминальная ферма: реализация и приёмка пилота

Цель — Linux-ферма на Astra Linux SE 1.8 с доменными учётными записями,
персональными пользовательскими данными, рабочим столом и опубликованными
приложениями. Первый клиент — штатный X2Go Client на Windows; собственный
интерфейс клиента добавляется после проверки доставки сессий.

Брокер управляет назначением узлов; пользовательские процессы выполняет X2Go
Server на узлах. Виртуальные машины, ввод в домен, пользовательское хранилище,
резервное копирование и политики ОС не создаются текущим кодом автоматически.
Опубликованная 1С требует совместимого Linux-клиента платформы и проверки
конкретной конфигурации. Произвольные Windows-приложения эта архитектура не запускает.

## 1. Исправления перед подключением пользователей

Первый PR:

- Исправить трактовку успешного `ldap3.Connection.open()`; ошибку поиска группы
  считать ошибкой авторизации, не выдавать роли из неполного ответа.
- Различать пустой список сессий и ошибку серверной утилиты.
- Проверять структуру ответа и метрики агента до обновления состояния узла;
  повреждённый ответ одного узла не должен прерывать опрос остальных.
- Завершать сессии штатной утилитой от имени владельца. При её ошибке не убивать
  root-процесс по непроверенному PID из БД.
- Принимать клиентское событие только для известной сессии владельца на узле
  разрешённого пула; сопоставлять событие по паре узел/идентификатор сессии.
  Событие до появления сессии в опросе отклоняется. Клиентские сведения остаются
  недоверенной телеметрией, а не доказательством личности устройства.
- Запускать регрессии в CI, включая одновременное назначение мест.

Это исправление известных дефектов, а не подтверждение готовности к эксплуатации.

## 2. Минимальный стенд

| Компонент | Назначение |
|---|---|
| ВМ брокера | Nginx/TLS, брокер, SSH-ключ доступа только к агентам |
| Два терминальных узла | Одинаковая Astra, X2Go Server, окружение рабочего стола и версии ПО |
| AD rrcki.ru | Доменные пользователи, отдельные группы доступа к пулам и роли панели |
| Пользовательское хранилище | Согласованные UID/GID, права, квоты, резервное копирование |
| Windows-рабочее место | X2Go Client с доверенным сертификатом брокера |
| Сборщик журналов | Внешняя копия событий и оповещение о потере доставки |

Первый тестовый пул — рабочий стол на двух узлах. После проверки входа,
переподключения и отказов добавить отдельный пул 1С. Узел может входить только
в один пул: для двух пулов с резервированием нужны четыре узла.

## 3. Доступ должен контролироваться на каждом узле

Клиент подключается к назначенному серверу напрямую по SSH. Поэтому проверки
групп в брокере недостаточно: на узлах нужны правила SSSD/PAM/sshd, разрешающие
доменный вход только группам их пула и отдельно определённым администраторам.
Конкретные параметры выбираются после проверки способа ввода Astra в домен.

Проверить прямое подключение, минуя брокер:

1. Участник группы своего пула входит.
2. Пользователь только другого пула получает отказ.
3. Обычный доменный пользователь без групп доступа получает отказ.
4. Служебный ключ брокера выполняет только команды агента; shell, PTY и
   SSH-перенаправления недоступны.
5. Пароль и членство отозванной учётной записи перестают давать доступ в пределах
   документированного срока кэшей брокера и ОС. Уже открытая сессия — отдельный
   случай; нужен согласованный порядок её завершения.

`rootless` и запрет редактирования профиля клиента не являются изоляцией приложения.
Ограничения запуска программ, устройств, буфера обмена, печати и файловых
перенаправлений необходимо задавать и проверять отдельно на узлах.

## 4. Приёмка реальных интеграций

| Сценарий | Условие приёмки |
|---|---|
| LDAP | Правильный пароль работает; неверный и пустой отклоняются |
| TLS каталога | Недоверенный сертификат или отказ StartTLS не приводят к передаче пароля по открытому соединению |
| Контроллеры | Проверено переключение при недоступности первого DC и измерено время входа |
| Группы | Проверены вложенные группы, отсутствие доступа к чужому пулу и роли панели |
| Рабочий стол | Новый вход, suspend/resume и reconnect проверены настоящим X2Go Client |
| Приложение | 1С открывает нужную базу; проверены шрифты, печать, вложения и лицензирование |
| Сессии | Ошибка штатного завершения видна в панели и аудите; посторонние процессы не затрагиваются |
| Обслуживание | Новые сессии обходят выведенный узел; существующие возобновляются |
| Отказ агента | Ошибка чтения сессий не выглядит как пустой исправный узел |
| Данные | Файлы и настройки доступны на обоих узлах, права и квоты действуют, восстановление проверено |
| Нагрузка | Измерены время входа, отклик, RAM, CPU, дисковые задержки и нагрузка хранилища |

Лимит пользователей на узел задаётся по замерам реальных приложений. Порог из
примерного конфига не является подтверждённой ёмкостью.

## 5. Что нужно решить до промышленной эксплуатации

- Отказ связи с узлом не доказывает остановку его пользовательских процессов.
  Автоматическая выдача второй сессии на другом узле может создать две активные
  сессии с одним общим профилем. Проверить сетевое разделение и определить политику
  повторного входа/блокировок/ограждения узла до использования общих домашних каталогов.
- VRRP переносит адрес брокера, но не синхронизирует резервы, блокировки входа и
  изменения обслуживания. Нужны проверенный active/passive-порядок, защита от
  двух активных экземпляров и согласованное состояние.
- `/healthz` сейчас подтверждает только работу HTTP. Нужны readiness по свежести
  опросов, наблюдение за AD, пулом и внешней доставкой журнала.
- Цепочка локальных хешей не подтверждает полноту журнала и не заменяет внешнее
  хранилище. Нужны контрольные значения, ротация с проверкой архивов и оповещение
  при невозможности записи или доставки.
- Ограничить число запросов/соединений, измерить время входа при недоступном AD,
  определить таймауты и проверить массовые подключения за NAT.
- Подготовить воспроизводимую установку, обновление, откат и резервное копирование
  конфигурации, состояния и ключей. Затем выпускать собственный клиент без изменения
  протокола доставки на первом этапе.

## Последовательность работ

1. Принять исправления и CI после просмотра PR.
2. Развернуть стенд и проверить реальный доменный вход и права на самих узлах.
3. Проверить данные, переподключения, отказ узла и сетевое разделение.
4. Подключить пул 1С и провести нагрузочные замеры.
5. Закрыть отказоустойчивость, наблюдение и обновления; допустить ограниченный пилот.
6. Развивать корпоративный клиент на проверенном серверном контуре.
